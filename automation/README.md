# Automation

## 模块作用

用于存放 AI Business OS 的自动化实现。

`workflows` 定义「做什么、按什么顺序做」；`prompts` 提供 AI 调用模板；`automation` 负责把这些流程落地为可重复执行的自动化任务——脚本、配置、调度与集成。

本模块的目标是：

- 减少重复性人工操作
- 保证流程执行的一致性与可追溯性
- 让业务闭环（内容 → 获客 → 私域 → 成交 → 交付 → 复购）中的关键环节可自动触发、可监控、可恢复

自动化不是替代思考，而是把已验证的流程固化下来，让团队把时间花在判断与优化上。

---

## 内容范围

### 应放入本模块

| 类型 | 说明 | 示例 |
|------|------|------|
| 脚本 | 可独立运行的自动化程序 | 内容发布、数据同步、报表生成 |
| 工作流配置 | 第三方自动化平台的导出或配置 | n8n、Make、Zapier、Cursor Automations |
| 调度定义 | 定时任务与触发规则 | cron、GitHub Actions、Windows 计划任务 |
| 集成连接器 | 与外部系统的对接说明与配置 | 飞书、企微、Notion、公众号 API |
| 运行文档 | 部署、环境变量、故障排查 | 每个自动化任务的 README 或 runbook |

### 不应放入本模块

- 纯流程设计文档 → 放入 `workflows/`
- Prompt 模板 → 放入 `prompts/`
- 长期知识沉淀 → 放入 `knowledge/`
- 产品说明与销售材料 → 放入 `products/` 或 `docs/`

### 推荐子目录结构

```
automation/
├── scripts/          # 可执行脚本（Python、Node、Shell 等）
├── configs/          # 第三方平台配置与导出文件
├── schedules/        # 调度与 CI/CD 定义
├── integrations/     # 外部系统集成（按平台或业务域划分）
└── runbooks/         # 运行手册与故障排查文档
```

子目录可按业务域进一步划分，例如 `scripts/content/`、`integrations/wecom/`。

## 文件命名规范

### 通用规则

- 使用英文、小写、中划线（kebab-case）
- 名称应体现「业务域 + 动作」，而非实现细节
- 版本号仅在需要并存多版本时使用

### 命名模式

| 文件类型 | 格式 | 示例 |
|----------|------|------|
| 脚本 | `{domain}-{action}.py` / `.js` / `.sh` | `content-publish-wechat.py` |
| 配置 | `{platform}-{workflow}.json` / `.yaml` | `n8n-lead-sync.json` |
| 调度 | `{frequency}-{task}.cron` / `.yml` | `daily-report.yml` |
| 运行文档 | `{task-name}-runbook.md` | `content-publish-runbook.md` |
| 环境模板 | `.env.example` 或 `{task}.env.example` | `wechat-api.env.example` |

### 禁止事项

- 不要使用空格、中文文件名或驼峰命名
- 不要在文件名中硬编码密钥、Token、密码
- 不要使用 `final`、`new`、`test2` 等无意义后缀

## 写作规范

每个自动化任务都应有对应的说明文档（可在任务目录下的 `README.md`，或在 `runbooks/` 中单独维护）。

### 必备章节

1. **目标** — 这个自动化解决什么问题，对应哪条业务链路
2. **触发条件** — 手动 / 定时 / 事件驱动；频率与前置条件
3. **输入** — 所需数据源、API、凭证、环境变量
4. **执行步骤** — 核心逻辑说明；复杂流程附流程图或步骤列表
5. **输出** — 产出物、写入位置、通知方式
6. **依赖** — 运行时、第三方服务、关联的 `workflows/` 或 `prompts/`
7. **失败处理** — 常见错误、重试策略、告警与人工介入点
8. **验证方式** — 如何确认任务执行成功

### 脚本写作要求

- 入口清晰：支持 `--help` 或顶部注释说明用法
- 配置外置：密钥与可变参数通过环境变量或配置文件注入，不硬编码
- 日志可追踪：记录开始时间、关键步骤、错误信息与执行结果
- 幂等优先：重复执行不应产生重复副作用（如重复发文、重复扣款）
- 失败可恢复：支持断点续跑或明确提示需人工处理的步骤

### 文档风格

- 用完整句子，避免只有关键词的清单式堆砌
- 步骤用有序列表，配置项用表格或代码块
- 涉及外部 API 时注明文档链接与权限范围

## 维护规范

### 准入标准

- 流程已在 `workflows/` 中验证可行，再进入自动化实现
- 上线前在测试环境或沙箱账号完成至少一次端到端验证
- 必须提供 `.env.example` 或等效的环境变量说明，不得提交真实密钥

### 变更管理

- 行为变更需更新文档中的「输出」与「验证方式」章节
- 破坏性变更（接口、调度时间、数据格式）需在文档顶部注明变更日期与迁移说明
- 关联的 `workflows/` 或 `prompts/` 变更时，同步检查本模块是否需调整

### 日常维护

- 定期审查调度任务是否仍符合业务需求，下线不再使用的自动化
- 监控失败率与执行耗时；连续失败的任务优先修复或暂时禁用并标注原因
- 第三方 API 或平台规则变更时，及时更新 `integrations/` 与对应 runbook

### 安全与合规

- 密钥、Token、Webhook URL 仅存放在本地或密钥管理服务，不入库
- 涉及用户数据的脚本需说明数据范围、留存策略与脱敏方式
- 对外部系统的写操作（发布、发送、扣费）需有人工确认或二次校验机制

### 协作原则

- AI 可辅助生成脚本与文档，但上线前需人工审核逻辑与权限
- 一人负责一个自动化任务的端到端 ownership（代码 + 文档 + 监控）
- 新成员可通过 runbook 独立部署与排错，无需口头交接

## 与其他模块的关系

```
workflows/   → 定义流程（做什么）
prompts/     → 提供 AI 能力（怎么说、怎么生成）
automation/  → 落地执行（怎么跑、怎么连、怎么管）
knowledge/   → 沉淀经验（为什么这样做、踩过什么坑）
```

新增自动化时，建议先在 `workflows/` 中明确流程，再在本模块实现；执行中积累的可复用经验，整理后写入 `knowledge/`。
